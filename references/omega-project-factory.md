# OMEGA Project Factory 25.3.0 — operational boundaries

Four supported deterministic project formats: `web`, `game`, `android`, `api`. Use the connected GitHub owner account and issues `[THOR-PROJECT] <kind> <slug>` to invoke the existing OIDC-bound Lovable inference service. The requester must be the repository owner. Source code templates are not dynamically generated by the model: the model supplies validated product metadata (name, tagline, accent), while trusted code emits projects. This is deliberate defense against arbitrary agent-command execution.

For project creation tests locally, invoke `node --test tests/omega-project-factory.test.mjs tests/omega-project-agent.test.mjs tests/omega-project-gate.test.mjs`. The model integration test uses a local stand-in and does not prove provider accessibility; the GitHub Actions execution and task evidence are required for live verification.

Core file hash gate is available in `hooks/omega-project-gate.mjs`; generated Android source does not prove an APK or device test. For native shipping, a separate Android SDK build, instrumentation and signing pipeline is mandatory. No automatic merge, no cross-account access, no raw token logging.

The project factory does not supersede existing OMEGA mobile skills or the canonical THOR API. It adds a real supported artifact production lane with review and evidence.
